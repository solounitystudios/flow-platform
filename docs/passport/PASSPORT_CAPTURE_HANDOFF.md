# Flow Creative Capture — Passport Evidence Bridge: Handoff

**Why this exists.** `/workspaces/flow-creative-capture` did not exist in the
workspace when the Passport V2 wave ran, so no Capture-side code was written or
modified. The Flow Platform side is complete and verified; this document is the
exact contract plus a ready-to-run implementation prompt for the Capture session.

Read first: [PASSPORT_CAPTURE_CONTRACT.md](./PASSPORT_CAPTURE_CONTRACT.md).

## Preconditions (Flow Platform side — already done)

* Contracts package: `packages/passport-contracts` (types, zod schemas, generated JSON Schema, signing).
* Gateway routes: `app/api/passport/v2/*` (need `SUPABASE_SERVICE_ROLE_KEY` + `PASSPORT_GATEWAY_CLIENTS` at deploy).
* **Not done, blocked on a product decision:** any Flow-side control that *creates* a
  capture request. A "Request capture" button would create requests that nothing can
  fulfil until Capture is connected, so none was added. When Capture ships, that
  control belongs next to the evidence surface (see contract → "Capture cannot create
  capture requests"). The Flow-side RPC `passport_create_capture_request` and its typed
  wrapper `createCaptureRequest` already exist and are tested.

## What Capture must do

1. **Obtain the contract from Flow — do not copy it.**
   Preferred: `@flow/passport-contracts` from a private registry. Until one exists:
   `npm pack` from `packages/passport-contracts` and install the tarball. A
   non-TypeScript stack uses `packages/passport-contracts/schemas/*.schema.json`.
2. **Be given** (deployment config, never committed): a client id `flow_capture`, a
   `key_id`, a secret (≥ 32 chars, generated by whoever operates Flow), and the base URL.
3. **Receive a request id** from the Flow experience that started the capture (deep link,
   QR token, or in-app handoff — Flow decides; the id is the only thing Capture needs).
4. `GET /api/passport/v2/capture-requests/{id}` → validate with `CaptureRequest`. Honour it:
   evidence type, `expires_at`, `required_metadata` (must appear in `source_metadata`),
   `location_policy` / `operator_identity_policy` (send `location` / `operator`
   **only** when `optional`, and only if the user consents in Capture's own UI).
5. Report lifecycle as it really happens — `accepted` when the user opens it, `started`
   (with Capture's session id) when capture begins, `failed` (with a `reason_code`) if it
   does. **Only report what is true**; do not invent states.
6. Create Capture's own media/artifact records (Capture owns them), then build an
   `EvidencePackage` **by reference** (`storage.provider: "flow_capture"`, an opaque `ref`;
   never inline bytes) with `sha256`/`byte_size` per artifact when known, and optionally
   `integrity.artifacts_digest = computeArtifactsDigest(artifacts)`.
7. `POST /api/passport/v2/evidence-packages`, signed. Persist the package and its
   `idempotency_key` **before** sending so a crash or timeout retries the **same** key and
   content with a **new** nonce/timestamp.
8. Treat the receipt as "received", **not** "verified" — never show a verified state.
9. **Never break the user's capture because Flow is unreachable.** Queue and retry with
   backoff on `retryable` errors and network failures; surface a user-visible
   "couldn't send to Passport yet — will retry" state (not a silent failure). Do not retry
   non-retryable errors; surface them.

## What Capture must NOT do

* Write to any Flow database table, or call Supabase directly with any key.
* Copy Passport rules (verification, consent, authority) into Capture.
* Decide identity, credentials, or verification. Capture produces evidence.
* Send location or operator identity the request did not permit.
* Embed media in the package, or log secrets/signatures.
* Create capture requests about a subject.

## Suggested Capture-side structure

* `passportBridge/client.ts` — signed fetch wrapper (uses `signRequest`), retry policy, error mapping.
* `passportBridge/mapper.ts` — Capture session → `EvidencePackage` (pure, unit-tested).
* `passportBridge/outbox` — durable outbox of packages/status reports with their idempotency keys.
* A user-visible integration state: `not_connected | sending | sent | will_retry | failed(reason)`.

## Tests Capture should have

* Valid package accepted → receipt `verification: "none"`.
* Retry after timeout re-sends the **same** idempotency key + content, **new** nonce.
* Duplicate receipt (`200`, `duplicate: true`) treated as success.
* `409 idempotency_conflict` and every `422` treated as non-retryable, surfaced to the user.
* `410 request_expired` / `409 request_not_open` handled (stop, tell the user).
* `503` / `500` / network error → queued with backoff, Capture keeps working offline.
* Location/operator omitted when the request forbids them.
* Contract conformance: the mapper's output parses with `EvidencePackage` from the shared package.

> Evidence Bridge (client side only)** described in
> `/workspaces/flow-platform/docs/passport/PASSPORT_CAPTURE_CONTRACT.md` and
> `PASSPORT_CAPTURE_HANDOFF.md`. First: `git status --short --branch`,
> `git fetch origin --prune`, `git rev-parse HEAD origin/main`. If the working tree is
> dirty or a conflicting Passport/Capture integration branch exists, STOP and report. Otherwise
> create `feat/passport-evidence-bridge-v1`.
>
> Rules: consume `@flow/passport-contracts` (or its generated JSON Schemas) from Flow — never
> duplicate the contract. Sign every request with `signRequest`. Never write to a Flow
> database; never copy Passport verification/consent/authority logic. Capture creates media
> and artifact records; the bridge maps a completed capture session to an `EvidencePackage` by
> reference and delivers it. Persist the package + idempotency key before sending; retry the
> same key/content with a fresh nonce; treat `duplicate: true` as success; never present
> "received" as "verified"; surface integration failure to the user; keep Capture fully usable
> when Flow is down. Add the tests listed in the handoff. Commit and open a PR in the
> Capture repo only — never commit Capture and Flow files together. Report what you verified
> and what you could not (deployment secrets are required to run against a real Flow).
